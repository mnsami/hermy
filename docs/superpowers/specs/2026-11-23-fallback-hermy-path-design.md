# Fallback lines run the plugin's own hermy (#157)

## Intent

On a host that does not inject or expand (Copilot, any agent reading `AGENTS.md`), the skills' fallback lines and the `AGENTS.md` block ran bare `hermy <verb>`, so `PATH` picked the binary: a project's own `bin/hermy` (a `.` or `./bin` entry), a stale `get.sh` install, or none. `sweep` writes. Only the right `hermy` may run.

## Shipped behaviour

- Every skill's fallback line runs `'<plugin dir>/bin/hermy' <verb>` by absolute path, single-quoted, a `'` in it written `'\''`, `<plugin dir>` being the directory that holds this skill's `skills/<name>/SKILL.md`, never one inside the project, the main checkout (the parent of `git rev-parse --path-format=absolute --git-common-dir`, spelled with `pwd -P`; where its first line is `--path-format=absolute`, as a git before 2.31 (Ubuntu 20.04's 2.25, Debian 11's 2.30) prints the flag back before a relative `.git`, `cd` from the working directory into the parent of plain `git rev-parse --git-common-dir` and take `pwd -P`, so such a git still places a git-only repository), nor inside the checkout the agent runs in or a worktree of the repository (`git worktree list`, and `jj workspace list --ignore-working-copy --no-pager -T 'if(root, root ++ "\n")'` in a jj repository, the template there since it prints no path by default), each compared physically, links followed. Unknown, or no `bin/hermy` there → stop and say so. `jj workspace root --ignore-working-copy --no-pager` succeeding and lying physically below `git rev-parse --show-toplevel` (a jj repository nested in another git repository: a `$HOME/.git` dotfiles repository, whose top level git reaches past `.jj`, would put the plugin dir inside the checkout), or git's placement there failing or giving anything but one absolute path (a jj repository with no `.git`) → place them through jj: the main checkout is `jj workspace root` run in the default workspace, or the directory `.worktrees/` sits in, the agent's checkout `jj workspace root`, and the worktrees `jj workspace list` alone, never `git worktree list`, which in a `$HOME/.git` dotfiles repository lists `$HOME` and would put the plugin dir inside a worktree, every jj command written with `--ignore-working-copy --no-pager`, since without it jj snapshots the working copy (an operation written, the main checkout's untracked files tracked) and runs a signing program a planted repo config names, which the hooks' own jj calls avoid the same way; git's placement only where jj gives no root or one at or above git's; only where neither git nor jj places them → stop and say neither can place the project there, so a jj repository with no `.git`, which ran before this change, still runs. That definition and its stops apply only under the fallback conditions (a section shows its command rather than its output, or `CLAUDE_PLUGIN_ROOT` is unexpanded), so a host that injects never stops on it. No fallback line runs a `hermy` by any other path, anywhere in a command: after a `;`, inside a `$(`, behind `cd x &&`, `env` or `command`, nor the block's own forms (`'<hermy>'`, the `get.sh` path), which no fallback line defines.
- The `AGENTS.md` block never runs `hermy` from `PATH` and never resolves it there (`command -v hermy`). It places the checkouts, the main one, the agent's and every worktree of the repository, as the fallback lines do, through jj where jj's root lies below git's or git cannot place them, else through git, and stops only where neither can; inside a checkout is compared physically, links followed. The hermy plugin's own `config` skill listed for the session is the agent's source, told before any load: by a `SKILL.md` the listing shows outside every checkout, or by the host's label for a plugin's skill (`hermy:config` in Claude Code, never an unprefixed `config`, which a `.claude/skills/config/` planted in the project carries, with hermy's description) only where no checkout, nor the directory the agent runs in, holds `hermy/.claude/skills/config/SKILL.md`, since Claude Code lists that directory-scoped skill under the same `hermy:config` label (a path prefix, as `apps/web:deploy`) and the listing alone cannot tell the two apart; checking that file exists loads nothing. It never takes a skill on its label alone, nor loads one to find where its `SKILL.md` lies, since the load has already run its injected commands; anything else falls through to `get.sh`'s install. It is read for its injected Current and Worktrees sections alone, whose commands only read, never for its steps, where the host injects, so an agent that injects (Claude Code reading the block) runs nothing undefined, else its fallback line's `'<plugin dir>/bin/hermy'`. One skill, named: any hermy skill would let the agent load `next`, `start` or `refresh`, whose injected `sweep` removes merged worktrees, or `ship` and `drop`, which run only on the user's ask. Never a directory-scoped copy (listed with a path prefix) nor one the listing shows inside a checkout: a sandboxed command or a merged PR can plant one (`.claude/skills/`, `.github/skills/`) whose fallback line runs the project's own `bin/hermy`. Otherwise the block runs `get.sh`'s install, the path `${HERMY_HOME:-$HOME/.hermy}/bin/hermy` expands to, held, as the skill is, to an absolute path outside every checkout (not absolute, or inside one → stop, naming the cause), single-quoted (`'<hermy>' config`), a `'` in it written `'\''`; missing or not executable → stop and tell the user to install or update it with `get.sh` from https://github.com/mnsami/hermy, the user's step, never the agent's. Its "Not installed" line, for a missing plugin, says the same.

## Non-goals

- No version check: the plugin's own `bin/hermy` is the plugin's version by construction, and `get.sh`'s install is the one the user chose.
- No new verb or flag in `bin/hermy`.
- The Claude Code path (shims by absolute path) is unchanged.
- Rewriting `AGENTS.md` in projects already onboarded: `onboard` stops whenever a config exists, so an existing block, the `command -v` one or the bare-`hermy` one before it, stays as it is until the user starts over or pastes the new block.

## Approaches

- A, chosen: the skills call `<plugin dir>/bin/hermy` by absolute path; the `AGENTS.md` block runs `get.sh`'s fixed install or defers to a listed skill, with no `PATH` lookup.
- B, cut: the `AGENTS.md` block resolves `command -v hermy` and walks every link and directory on the way against the main checkout, every worktree, the agent's checkout and its working directory by identity, as the core does for `HERMY_EXEC`. Five review cycles kept finding cases the prose walk missed (a directory link on `PATH` into the project pointing outside; `<hermy>` undefined on an injecting host that reads `AGENTS.md`), while a fixed path has nothing to walk.

## Ceilings

- `HERMY_HOME` is trusted as `get.sh` trusts it, within the block's rule: one set by the project's own environment (a `.envrc`, an agent settings `env`) points the block at whatever it names outside the checkouts (a directory under `TMPDIR` a sandboxed command can write included); one relative, or inside the main checkout, the agent's checkout or a worktree, stops it.
- An agent with no hermy skill listed and no `get.sh` install stops; it never falls back to `PATH`.
